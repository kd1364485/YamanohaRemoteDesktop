# 性能の測定

FramePipeline(キャプチャ → エンコード → 送信)の、ホスト側の処理時間を測った記録。2 回分ある。

1. **2026/11/06: 本物の画面**(デスクトップ PC)。この節。
2. 2026/11/02: ダミー画像(ノート PC。Desktop Duplication が使えなかった)。下の「2026/11/02 の測定」の節。

# 2026/11/06: 本物の画面での測定(デスクトップ PC)

## 条件

- 環境: AMD Ryzen 7 9800X3D、NVIDIA GeForce RTX 5070 Ti(16GB、ドライバ 610.88、GPU は 1 枚。CPU 内蔵の AMD Radeon は画面を出していない)、Windows 11(10.0.26200)、ディスプレイ 1 枚(2560x1600、60 Hz)。
- `dd_probe`: NVIDIA の出力 × NVIDIA のデバイスで、`DuplicateOutput` が **`S_OK`**(`docs/bench_raw/dd_probe_output_desktop_rtx5070ti.txt`)。ノート PC の `DXGI_ERROR_UNSUPPORTED` は出なかった。ハイブリッド GPU 特有の問題だった可能性が高い(ノート PC 側で原因は確定していない)。
- `pipeline_bench.exe 15 60 4000 -1 3`: 2560x1600、60 fps 目標、4000 kbps(CBR)、NVENC。15 秒 × 3 回。`pipeline_bench` の事前確認で「本物の画面を取得できます」を確認した。
- 画面の内容: 色の付いた四角 6 つが動き、背景の色と、ミリ秒の時計が毎フレーム変わるブラウザのページ(全画面ではない)。画面が止まっているとエンコードを省くので、動かしておく必要がある。
- ビルド: Release、MSVC(Visual Studio 18 のジェネレーター。前回は Ninja)。
- **前回(1080p、ダミー画像)とは、解像度も PC も違う。そのまま比べない。**

## 結果

3 回それぞれの p50(p95)、単位 ms。生の出力は `docs/bench_raw/pipeline_bench_real_screen_default_timer.txt` と `..._timer_1ms.txt`(STUN で分かった公開 IP は `x.x.x.x` に伏せた)。

| 段階 | 既定のタイマー(約 15.6 ms) | タイマー 1 ms(`YAMANOHA_BENCH_TIMER_1MS=1`) |
|---|---|---|
| 1 キャプチャ取得 | 0.050 / 0.050 / 0.052 | 0.040 / 0.040 / 0.041 |
| 2 GPU 間コピー(CPU 経由) | 1.66 / 1.67 / 1.70(5.3 / 5.4 / 5.8) | 1.47 / 1.46 / 1.46(3.3 / 3.3 / 3.3) |
| 3 エンコーダへの投入 | 0.16 / 0.16 / 0.16 | 0.14 / 0.14 / 0.13 |
| 4 エンコード完了の待ち | 4.84 / 5.05 / 5.17(12.6 / 12.5 / 13.0) | 4.61 / 4.53 / 4.56(11.3 / 10.7 / 11.0) |
| 5 送信キューでの待ち | 0.01 | 0.01 |
| 6 送信呼び出し | 0.14 / 0.14 / 0.15 | 0.13 / 0.13 / 0.13 |
| **合計(取得開始 → 送信呼び出し完了)** | **6.90 / 7.10 / 7.23**(17.0 / 16.9 / 18.8) | **6.43 / 6.38 / 6.41**(15.0 / 14.4 / 14.7) |
| **FPS** | **29.9 / 29.7 / 29.8** | **41.2 / 41.8 / 41.2** |
| ビットレート(平均) | 1,565〜1,591 kbps | 2,064〜2,112 kbps |
| データチャネルの往復(p50、µs) | 221 / 220 / 222 | 143 / 137 / 140 |

- どの回も、バックログでの見送り 0、取得の失敗 0、送信の失敗 0。
- フレームの大きさは平均約 6.4KB。画面が単純なので、CBR 4000 kbps に届いていない。

## 分かったこと

### 1. キャプチャの取得そのものは、ほぼゼロ(約 0.05 ms)

Desktop Duplication は、GPU 上のテクスチャを渡すだけなので速い。前回のノート PC の「約 5.6 ms」は、ダミー画像を作る時間だった、という推測と合う。

### 2. FPS が約 30 に止まる原因の 1 つは、タイマーの粒度

ホスト内の 1 フレームの処理は約 7 ms なのに、FPS は約 30(周期 約 33 ms)。キャプチャのループは、フレームを送ったあと、フレーム間隔(16.7 ms)の残りを `sleep_for` で待つ。新しいフレームがなければ、1 ms 待ってやり直す。既定の粒度は約 15.6 ms で、どちらの待ちも次の刻みまで延びる。その結果、1 周が 2 刻み(約 31 ms)になる、と考えた。

タイマーの粒度を 1 ms にすると、**3 回とも 41 FPS 台に上がった**(既定は 3 回とも 29.7〜29.9)。前回のノート PC では、ダミー画像の時間が混ざったせいか、結果が一貫しなかった(47.0 / 36.8 / 37.1)。本物の画面では、はっきり差が出た。

- **まだ分からないこと**: 1 ms にしても 60 に届かない理由。候補は 2 つ。1 つは、測定に使ったページの描画が、毎フレームは更新されていないこと。もう 1 つは、待ちが明けた時点で次のフレームがまだなく、1 周むだにすること(画面の更新の周期と、ループの周期がずれる)。どちらも確かめていない。ページの実際の描画の頻度を測る、または `AcquireNextFrame` に待ち時間を渡して、画面の更新に合わせて起きる作りにすると、切り分けられる。
- アプリ本体(`FramePipeline`)は、タイマーの粒度を変えていない。直すなら、`timeBeginPeriod(1)` を使うか、待ちを `AcquireNextFrame` のタイムアウトに任せる。どちらも未実装。

### 3. タイマー 1 ms では、ほかの段階も速くなった

GPU 間コピーの p95 が 5.3〜5.8 → 3.3 ms、データチャネルの往復が 0.22 → 0.14 ms。CPU が深い省電力の状態に入りにくくなったため、と推測している(確かめていない)。

### 4. GPU 間コピーは、同じ GPU でも 1.5〜1.7 ms(2560x1600)

前回の発見 2 のとおり、カーソルを CPU 側で合成するため、同じ GPU でも、GPU → CPU → GPU と往復する。p95 は 3〜6 ms。処理時間の約 4 分の 1 で、GPU の中だけで済ませる改善の余地はそのまま(未実装)。

### 5. 測定プログラムの不具合: 受信側がパケットを読んでいなかった

前回も今回の 1 回目も、libdatachannel が「`Number of media packets dropped due to a full queue`」を毎秒 200〜300 件出していた(前回の生の出力にも 41〜43 回)。原因は、測定プログラムの受信側(ブラウザ役)が、映像のトラックを作っただけで、受け取ったパケットを読み出していなかったこと。`receive_track->onMessage(...)` で読み捨てるようにすると、**警告は 0 件**になった。送信側の数字(コピー、エンコード、送信呼び出し)は、直す前とほぼ同じ(1 回目の合計 p50 6.9〜7.1 ms)。アプリ本体の問題ではなく、測定プログラムの問題。

## この測定の限界

- 1 つの PC、1 つの解像度、1 種類の画面の内容(単純なページ)。動画や細かい文字の多い画面では、エンコードの時間とフレームの大きさが変わるはず。
- 受信側はデコードも表示もしない。**画面が変わってから、クライアントに映るまでの遅延は、まだ測っていない**(別の端末が要る)。
- 各条件 3 回だけ。

# 2026/11/02 の測定(ノート PC、ダミー画像)

**この測定には、重要な制限がある。先に読むこと。**

## 先に読むこと: 何が測れて、何が測れていないか

| | 内容 |
|---|---|
| **測れた** | GPU 間コピー、エンコード(NVENC)、送信キュー、送信呼び出し、同一 PC 内のデータチャネルの往復時間 |
| **測れていない(重要)** | **本物の画面のキャプチャ。** 測定した PC では Desktop Duplication が使えず、パイプラインが「ダミー画像のモード」で動いた(下の「発見 1」)。キャプチャ取得の時間と FPS は、実際の画面のものではない |
| 測れていない | 画面が変わってから、クライアントの画面に映るまでの遅延(ネットワーク、デコード、表示)。受信側は映像を受け取って捨てる。これには別の端末が要る |
| 影響する | 測定中の PC の負荷。同じ条件でも、回によって大きくぶれた(下の「測定の限界」) |

## 測定の方法

- **本物の `FramePipeline`** を動かす。段階ごとに時刻を記録するコード(`src/pipeline/stage_stats.h`)を、`YAMANOHA_STAGE_STATS` を定義したビルドでだけ有効にする。通常のビルドでは、マクロが空になって何も残らない。
- 送信側は本物の `WebrtcStreamer`。受信側は、同じプロセス内の素の libdatachannel(実際のアプリでブラウザが担う役割)で、映像を受け取って捨てる。
- 測定プログラム: `native/test/pipeline_bench.cpp`(ターゲット `pipeline_bench`)。
- **本物の画面を取得できない場合は、測定を中止する**(環境変数 `YAMANOHA_BENCH_ALLOW_DUMMY=1` を付けたときだけ、ダミー画像で続ける)。ダミー画像の数字を、本物と間違えないための安全装置。
- 条件: 1920x1080、60 fps、4000 kbps(CBR)、NVENC(P1、低遅延)、Release ビルド(MSVC、Ninja)。1 回 15 秒を 3 回。

環境: Intel Core i7-12700H、NVIDIA GeForce RTX 3060 Laptop GPU(6GB)、Intel Iris Xe、Windows 11(10.0.26100)。

## 結果: 段階ごとの所要時間(ダミー画像、タイマーは既定)

3 回の測定の p50 / p95 / 平均(µs)。生の出力は `docs/bench_raw/pipeline_bench_default_timer.txt`。

| 段階 | p50 | p95 | 平均 | 備考 |
|---|---|---|---|---|
| 1 キャプチャ取得 | 5,612 / 6,177 / 5,846 | 6,497 / 6,947 / 6,758 | 5,671 〜 6,215 | **無効**(ダミー画像を返す処理の時間と思われる) |
| 2 GPU 間コピー | **2,498 / 2,479 / 2,496** | **7,995 / 7,907 / 8,079** | 3,702 〜 3,779 | 2 つの山がある(p50 と p95 が大きく違う) |
| 3 エンコーダへの投入 | 288 / 273 / 281 | 446 / 411 / 432 | 292 〜 307 | 実際のエンコードの完了は、次の段階で待つ |
| 4 エンコード完了の待ち | **4,710 / 4,781 / 4,781** | 8,206 / 8,344 / 8,388 | 5,375 〜 5,448 | NVENC が 1080p の 1 フレームを処理する時間 |
| 5 送信キューでの待ち | 14 / 14 / 14 | 57 / 59 / 31 | 17 〜 18 | ほぼゼロ |
| 6 送信呼び出し | 209 / 203 / 209 | 305 / 279 / 312 | 215 〜 223 | 約 0.2 ms |
| **合計(取得開始 → 送信呼び出し完了)** | **13,578 / 14,142 / 13,666** | 22,291 / 23,014 / 22,472 | 15,396 〜 15,885 | 無効な「1」を含む |

- FPS: 35.8 / 35.5 / 35.8(目標は 60)。ビットレートは約 2,290 kbps(フレームは約 8KB、CBR の 4000 kbps ÷ 60 fps ≒ 8.3KB と合う)。
- バックログによる見送り 0 回、送信失敗 0 回。
- **データチャネルの往復時間**(同一 PC 内): p50 349 / 357 / 378 µs、p95 510 〜 624 µs、p99 610 〜 753 µs(最大は 783 〜 5,055 µs)。マウス操作などの制御信号が通る経路で、ネットワークを含まない下限の目安。

**ダミー画像のモードでも有効なのは、2 〜 6 の段階。** 画面の内容が違うと、エンコード時間やフレームのサイズは変わりうる(ダミー画像の中身は確かめていない)。

## 発見

### 発見 1: この PC では、Desktop Duplication が使えない(`DXGI_ERROR_UNSUPPORTED`)

`DuplicateOutput` が、**全アダプタ × 全出力の組み合わせ**(NVIDIA、Intel、ソフトウェア描画)で `DXGI_ERROR_UNSUPPORTED` を返した。`DuplicateOutput1` も同じ。HDR はオフ(ColorSpace=0、8 bit)で、原因ではない。サンドボックスの外(通常のターミナル)でも、同じ結果。元の Debug ビルド(`encode_test.exe`)でも、同じ失敗とダミー画像への切り替えが起きる。出力は `docs/bench_raw/dd_probe_output.txt`、診断用プログラムは `native/test/dd_probe.cpp`。

- この PC は Optimus 構成(Intel と NVIDIA)で、DXGI は内蔵ディスプレイを **NVIDIA 側の出力**として列挙する(Intel 側には出力が出ない)。一方、WMI は Intel が解像度を持つように見せる。この食い違いが関係している可能性があるが、**原因は確定していない**。
- 影響: **この状態では、FramePipeline は、黙ってダミー画像に切り替わる。** 画面が配信されない。ユーザーには、原因の分かるエラーが出ず、ログに 1 行出るだけ。
- 見直すとよい点: 失敗したときに、ダミー画像で動き続けるのではなく、利用者に分かる形で失敗を返す。ハイブリッド GPU で、`display.adapter_index` ではなく、実際に画面を駆動している GPU を選ぶ。

### 発見 2: 同じ GPU でも、画面のコピーは必ず CPU を経由する

`CopyToEncodeTexture` は、GPU のテクスチャ → CPU 上のステージング → カーソルの合成 → もう一度 GPU へ、という経路を**常に**通る。この PC では、キャプチャとエンコードが同じ NVIDIA の GPU でも、同じ。
**p50 約 2.5 ms、p95 約 8 ms**(1080p の 1 フレーム、約 8MB)で、処理時間の約 4 分の 1 を占める。
CPU を経由するのは、カーソルを CPU 側で合成しているため。カーソルの合成を GPU 側(シェーダーやブレンド)に移し、同じ GPU のときは GPU 内でコピーする、というのが、1 つの改善案(**未実装、未検証**)。

### 発見 3: エンコーダの完了待ちが、処理時間の約 3 分の 1

「エンコード完了の待ち」が p50 約 4.7 ms。同期モードでも、`SubmitFrame` が 0.3 ms で戻り、実際の完了は `GetCompletedFrame` で待つ。ここは NVENC の処理時間そのもの。ただし、同じ条件で測った別の回では、9 ms 台まで伸びた(下の「測定の限界」)。

### 発見 4: FPS が目標の 60 に届かない(約 36)

1 フレームの処理(取得 + コピー + 投入)は約 10 ms なのに、実際の周期は約 28 ms。キャプチャのループは、残りの時間を `sleep_for` で待つ作りで、**Windows の既定のタイマー粒度(約 15.6 ms)**で待ち時間が切り上がっているのでは、という仮説を立てた。
検証としてタイマー粒度を 1 ms に上げて測り直したが、結果が一貫しなかった(FPS は 47.0 / 36.8 / 37.1)。**仮説は、確認も否定もできていない。**
(ダミー画像の生成時間を含むので、本物の画面で同じとは限らない。)

### 発見 5: WebRTC の接続開始まで、0.1 〜 約 24 秒かかることがある

`WebrtcStreamer` は、ICE 候補の収集が**すべて終わるまで** Offer を出さない。この PC では、4 回の測定のうち 3 回が約 23.6 秒、1 回が 0.1 秒だった。STUN サーバー(3 つ設定されている)のどれかの応答待ちが、長引いていると推測される(**未確認**)。
改善案: 収集の途中で Offer を出す(Trickle ICE)、または、STUN サーバーへの応答待ちに期限を付ける。

### 発見 6(測定中に見つかった、コードの不具合)

| 内容 | 場所 |
|---|---|
| **「track not open」の警告が、一度も表示されない。** `time_point::min()` を引き算するとオーバーフローして、条件が成り立たない。映像トラックが開いていないときの、送信失敗の原因が、ログに出ない | `webrtc_streamer.cpp`(`PushVideoFrame`) |
| `capture_test.cpp` が、今のコードではコンパイルできない(`DisplayManager` の名前空間指定がない)。`cmake --build` でプロジェクト全体を作ると失敗する | `native/test/capture_test.cpp` |
| `pipeline_primitives_test` は `assert` を使っているので、**Release ビルドでは何も検証しない**(`NDEBUG` で `assert` が消える) | `native/test/pipeline_primitives_test.cpp` |

これらは、記録のみ。修正はしていない。

## 測定の限界

- **ダミー画像で測っている。** 本物の画面のキャプチャ(段階 1)と、画面の内容によるエンコード時間の違いは、測れていない。
- 同じ条件でも、回によって大きくぶれた。タイマーを 1 ms にした 3 回では、GPU 間コピーの p50 が 3.0 → 6.4 → 6.4 ms、エンコード完了の待ちの p50 が 4.0 → 9.5 → 9.4 ms と、同じプロセスの中で悪化した(`docs/bench_raw/pipeline_bench_timer_1ms.txt`)。この PC は、性能コアと省電力コアの混在する CPU で、GPU・CPU の省電力の状態も変わりうる。原因は特定していない。
- 受信側は、デコードも表示もしない。実際のクライアントでは、デコードと表示の時間が加わる。
- 1 つの PC、1 つの解像度(1920x1080)、1 つのコーデック設定だけ。

## 再現手順

```powershell
# ビルド(Visual Studio の CMake / Ninja)。依存の取得にはネットワークが要る
cmake -S native -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build --target mbedcrypto mbedx509 mbedtls
cmake --build build --target pipeline_bench dd_probe

# 1. まず Desktop Duplication が使えるかを確かめる
.\build\dd_probe.exe

# 2. 測定 (秒数 fps ビットレート ディスプレイ番号 繰り返し)。画面に動きがある状態で
.\build\pipeline_bench.exe 15 60 4000 -1 3

# 3. Desktop Duplication が使えない PC で、ダミー画像のまま測るとき(キャプチャ取得の数字は無効)
$env:YAMANOHA_BENCH_ALLOW_DUMMY = '1'
.\build\pipeline_bench.exe 15 60 4000 -1 3
```

`datachannel.dll`(`build\_deps\datachannel-build\`)を、`pipeline_bench.exe` と同じフォルダに置く。
